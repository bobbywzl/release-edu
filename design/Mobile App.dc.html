Event loop blocking: why one slow handler stalls every request

{{ nodeProgressLabel }}

Your API is a restaurant with one waiter. He is quick, but there is exactly one of him: every request is a table, and the event loop is his route between them. He never stands still waiting — slow jobs like disk and network go back to the kitchen, and he returns only when a plate is ready.

Blocking is the waiter stopping to cook at the table. Nothing else gets served — not because the restaurant is full, but because the only person who serves is stuck.

That is why one slow handler stalls every request. Three things cook at the table:

—Synchronous I/O: fs.readFileSync, blocking DB drivers
—Big CPU work on the thread: parsing a 40 MB JSON body, image resizing, crypto
—Tight loops that never yield back to the loop

Bob's sketch: the request's path through the loop

The fix is never “more cores” — your JavaScript runs on one thread no matter the hardware. The fix is getting the cooking out of the dining room: worker threads for CPU work, job queues for anything that can finish later.
